# Architecture

How macworx is built. SPEC.md says what it does; this file covers only what exists in the code.

## Folder map

| Path | What it holds |
|---|---|
| `src/` | The React app (Vite). `main.tsx` mounts `App.tsx`, which switches between screens. See "UI". |
| `src/screens/` | One component per screen: Home, Assignment, Result. `practice/SpellingPractice` is the Spelling sample (8 words, checked on the iPad, nothing stored or sent) and `practice/ReadingPractice` is the Reading sample (one passage, two questions, checked on the iPad, nothing stored or sent; her choices live in the component, so Read again keeps them). `practice/NextButton` is the Next button Math, Spelling and Reading share, and `practice/BackToHomeButton` is the Back to Home button Spelling and Reading share. |
| `src/components/` | Pieces of a screen: `NumberPad`, `StackedProblem`, `RewardIcon`. |

| `src/sync/` | Saving her results (`sync.ts`): taking a stored seed, queueing a result, and syncing with the Worker. `projection.ts` applies unsent results to the Worker's numbers for Home and the result. |
| `src/parent/` | The portal's calls (`api.ts`): every `/api/parent` call for the selected child, and reloading once when Access's sign-in has run out. Its tab addresses (`route.ts`), the remembered child (`selection.ts`), its icons (`icons.tsx`) and `shop.ts`, which works out which rewards her balance reaches. Pure helpers: `adjust.ts` (the amount, note and below-zero checks of an adjustment), `activity.ts` (what an activity log entry says, its kind and signed amount), `streakForm.ts` (the streak boxes as the Worker wants them) and `streakDays.ts` (the last-7-days strip, ranges and the preview). `getSummary` sends the browser's local day (`localDay()`) as `today`. |
| `src/screens/parent/` | The portal shell and router (`Portal.tsx`), the screens' contents (`ParentPage.tsx`), Overview's Children panel for adding and renaming a child (`ChildForm.tsx`, using `src/ui/Segmented.tsx`), the message and Try again shown when the children can't be listed (`ChildrenGate.tsx`), the marker for a number or list that hasn't arrived (`Pending.tsx`: "Loading…", then "Not available right now." once a read has failed), the Devices screen (`DevicesScreen.tsx`: a card per connected device and the pairing form; `GET /api/parent/devices` returns `lastResultAt`, the latest `results.created_at` of each device; the Online and browser-line sample data lives in `src/parent/placeholders.ts`), the Shop screen (`Shop.tsx`: rewards from `REWARDS`, read-only, nothing stored; no rewards or purchases table), the Macaronis screen (`PointsScreen.tsx` with its state hook `useAdjust.ts`), the Streak screen (`StreakScreen.tsx` with its state hook `useStreakForm.ts`), and the Overview screen (`Overview.tsx` over the pure helpers in `src/parent/overview.ts`: today's assignments, connected devices and last sync, and the four shortcut tabs). |
| `src/pairing/` | The iPad's pairing call: `/api/pair`. |
| `src/assignment/` | Pure helpers for the assignment screen: answer boxes and number pad typing. |
| `src/engine/` | The question engine, pure TypeScript (CLAUDE.md). See "Question engine". |
| `worker/` | The Cloudflare Worker that answers `/api/*`: routing (`index.ts`), device keys (`auth.ts`), the child API (`child.ts`), Access checks (`access.ts`), the parent API (`parent.ts`, with `children.ts` and `pair.ts` for its child and pairing routes), what every parent route shares (`parent-request.ts`: the request type and `childOf`) and the admin log write (`admin-log.ts`). The Worker's modules don't import each other in a circle (`worker/imports.test.ts` fails on one). `worker/test/` holds a local D1 for its tests. |
| `migrations/` | Numbered D1 SQL migrations, applied in order. See "Data". |
| `public/` | Icons, `logo.svg` and `_headers`, copied into the build as is. |
| `e2e/` | Playwright tests of the production build. |
| `scripts/` | The check scripts CI runs, the engine purity test, and `create-device.mjs`. |
| `.github/` | CI, security, release and merge-gate workflows, the `main` ruleset, Dependabot, PR and issue templates. |
| `.claude/` | nightshift's config for this repo (`nightshift.json`) and its release-issue text (PIPELINE.md). |

## Question engine

`src/engine/` holds every rule that decides what she earns, so the app and the Worker compute the same results. `index.ts` is its public API (SPEC §8). The app imports only from it.

| File | What it does |
|---|---|
| `config.ts` | The one config module: payout values, grade cutoffs, assignment shape, number ranges and the reward menu (each reward has an id, a name and a price). |
| `random.ts` | A seeded generator (mulberry32). |
| `problems.ts` | `generateAssignment(seed)`: 20 shuffled problems; the same seed always gives the same assignment, so the Worker can regenerate and re-score it. `makeProblem` computes an answer. |
| `score.ts` | `checkAnswer`: a whole number equal to the computed answer. |
| `streak.ts` | `nextStreak(state, today)`: dates come in as `YYYY-MM-DD` strings and are compared as day numbers, with no `Date` object or clock. |
| `payout.ts` | `payout`: base (the correct answers scaled to 20 by the result's size, so a math or reading result alike), accuracy bonus from the base, streak bonus and total, all whole-number math. |
| `reading.ts` | `scoreReading`: how many of a passage's questions she got right. |
| `grade.ts` | `grade`: the grade from the cutoffs in `config.ts`. |

Each file's tests sit beside it, named with their SPEC §7 IDs.

## UI

- **Screens:** `App.tsx` holds which screen is showing (home, an assignment with its seed, or a result) in React state. There's no router. What's saved lives in `src/storage/device.ts` (see "Saving results").
- **Parent portal** (as built; SPEC §5.3): `src/screens/parent/Portal.tsx` is the shell and the router. It is hand-rolled, with no router library: the five tabs are real `<a href>` links whose click does `history.pushState` (a modified click opens normally), a `popstate` listener follows Back and Forward, and `tabFromPath` in `src/parent/route.ts` maps any address to a tab (`/parent` and unknown `/parent/…` addresses show Overview and keep their address). Moving between tabs scrolls to the top and focuses the page title. The shell lists the children (`GET /api/parent/children`), picks the one remembered in this browser (`localStorage` key `macworx.parentChild`, otherwise the first; storage that refuses reads as nothing remembered) and calls `chooseChild` before the screens mount, so their first reads carry that child. The shell's state comes from the pure `childrenLoad` in `src/parent/selection.ts` (loading, ready, none, or unavailable). If the children can't be listed, the screens do not mount: `ChildrenGate` shows "We can't show your children right now." with Try again (which reads the list again and, once it loads, focuses the page title), or the sign-in message without the button when the sign-in has run out; a page reload for a sign-in shows nothing. A household with no children shows "No children yet." and `ChildForm` in Add only (it has no child to rename); adding the first child moves the shell to ready with the form still mounted. One DOM serves both layouts: the controls exist once and CSS moves them (phone: header on top and the tabs fixed at the bottom; from 768px wide: a 216px side bar). `ParentPage` holds all the screens' state and `refresh()` and takes `tab` to choose what to show, so switching tabs never refetches or clears a half-typed form; the shell remounts it (`key` = child id) when another child is chosen, and a `live` guard stops the replaced page's remaining reads. Colors are the `--p-*` tokens under `.parent`, and the portal's CSS is px only (`src/index.css`, between the `parent portal` comments; `src/parent/parentCss.test.ts` guards it). Home links to `/parent/overview` with a plain anchor, so it is a full page load that Access can intercept. `ParentPage` loads the four read views one after another, so a run-out sign-in reloads once, not once per call. It words log entries itself from `action` and `detail` (an unknown action reads as "Made a change"), and `formatCalendarDay` shows stored `YYYY-MM-DD` days without a time zone moving them. `App.tsx` renders `Portal` when the page loads under `/parent`; it's never a route inside her app, so every visit is a full page load that Access can intercept. Calls use `redirect: 'manual'`: a redirect or non-JSON answer below 500 means Access wants a sign-in, so the page reloads once (a `sessionStorage` flag stops a loop), then says the sign-in has run out; a JSON refusal is the Worker's own and shows a message, as does a Cloudflare error page (5xx). Her screens never use a text box; the parent page uses `src/ui/TextField`.
- **Pairing** (SPEC §5.4): `Home` shows **Pair this device** only when the app runs installed (`navigator.standalone` or `display-mode: standalone`) and has no key. The Pair screen reuses `NumberPad` (with a `checkLabel`) and the answer-box style (`CodeBoxes`). Each sync checks the stored key; a 401 forgets it, with the seeds and unsent results stored for it.
- **Devices screen** (SPEC §5.3): `DevicesScreen` has a left column (count, device cards) and a right column (the pair panel, "Before you disconnect", the Access card), one column in the phone's order below 1024px. The pair panel's state (name, code, countdown with its 15-second tick) lives in `ParentPage`, so a tab switch keeps it and a child switch clears it. The code is made for the chosen child through `scoped()` (`?child=`). The disconnect sentence is the pure builder `COPY.parentDisconnectSafe`.
- **Streak screen** (SPEC §5.3): `StreakScreen` shows the hero (streak, its range capped at 7 days, "Today ✓", and a sample Personal best from `src/parent/placeholders.ts`), the last 7 days (`weekStrip` over the days from `GET /api/parent/days`, read once, the first time the Streak tab shows) and the Correct a streak form. `useStreakForm` holds the boxes (filled from her numbers once) and the Review then Confirm step: Review checks the boxes with `streakFields` and locks them, Back unlocks them with the values kept, and Confirm posts once (`setStreak`).
- **Macaronis screen** (SPEC §5.3): `PointsScreen` shows the balance hero (`Summary.earnedToday` as "+N earned today", left out at 0), the Adjust balance form, and Recent activity (the admin log from `listLog`, one row each; `describe()` gives the title and, for a balance entry, the signed amount, with no balance before or after). It has three area wrappers in phone order (hero, adjust, activity) and a two-column grid from 1024px. `useAdjust` holds the form and the Review then Confirm step: `checkAdjust` decides whether Review is enabled, Review locks the fields, Back unlocks them with the values kept, and Confirm calls `submitAdjust`, which posts once (`adjustBalance`) and, on a 409, reads the summary again for the refusal line. Results that arrive after the page is replaced are dropped (`live`). `TextField` takes `multiline` for the reason box and `Segmented` takes `disabled`. There is no history route, so Recent activity has no "Full history" link.
- **Seeds:** a paired device takes the next stored seed (`takeSeed`), syncing first when it has none; with none and no connection, Home shows the Wi-Fi line. A device without a key practices with a random seed from `crypto.getRandomValues` and saves nothing. The engine never makes randomness itself.
- **Home numbers** (SPEC §5.1, §6.8): `App.tsx` keeps `numbers` from `homeNumbers(getWorkerState(), getQueue(), today)` and recomputes them when Home shows, after each sync and after a result is queued. They are absent without a key or before the first state arrives; `Home` then shows nothing extra. The finished `Outcome` carries the `Payout` from `nextResult`, so the result shows the streak bonus on the first assignment of the day. `Assignment` takes the same `numbers` and freezes them when it opens, so the top bar doesn't change mid-assignment. Without a key and a state the result's payout is the payout with no streak bonus.
- **Reward icons** (SPEC §6.7): `RewardIcon` draws one inline SVG per `RewardId` (a `Record`, so a reward without an icon fails type-checking), using only the color tokens. They are decorative (`aria-hidden`). No screen shows them yet.
- **Text:** every string she sees lives in `src/copy.ts`, including the grade headings, keyed by the engine's `Grade` type.
- **Shared building blocks:** The parent screens share the CSS classes `.parent-divider`, `.parent-note` (11 px muted footnotes and meta) and `.parent-chip` (with `-soft`, `-warn`, `-upper`), and every parent primary, secondary and soft button is a centered flex row with gap 8; `parentCss.test.ts` fails if a per-screen copy comes back. `src/screens/practice/ChoiceGroup`, `PracticeDone` and `InlineResponse` are the choices, the finished panel and the Check response line of Spelling and Reading. `src/ui/PracticePanel` is the panel of the practice screens (`.practice-panel`, variants problem, warm and soft; `check-conventions` fails on a hand-written one). `src/ui/Panel` is the panel of the parent screens (`.parent-section`; the Overview stat cards are panels with their own padding and gap; `check-conventions` fails on a hand-written one). `src/ui/SectionHeading` is the section title of the parent screens, with an optional action at the end of its row (`HeadingAction`). `src/ui/HeroPanel` is the hero panel of the Overview, Macaronis and Streak screens (shared `.parent-hero*` CSS; per-screen sizes under `.overview-hero`, `.points-hero` and `.streak-hero`; the unit shows only once the number has arrived). `src/ui/ReviewStep` is the one "Review, then Confirm" step of the parent portal (the Review button, then the confirm panel `.parent-review` with Confirm and Back, and focus following the step); the Macaronis and Streak screens use it, and Unpair keeps its own confirm. `src/ui/Safeguard` is the only notice row of the parent portal (`tone` info or warn, optional `icon`, `role`; `check-conventions` fails on a hand-written `.safeguard`). `src/ui/Button` is the only button, with variants `primary`, `secondary`, `key` and `check`, and the practice screens' `action`, `action-secondary`, `crumb`, `play`, `support` and `choice` (docs/DESIGN-PRACTICE.md §7.4). Their icons are in `src/practice/icons.tsx` (stroke 1.8). The Spelling samples (words, sentences, choices) and the Reading passage with its questions are in `src/practice/samples.ts`; `src/practice/speech.ts` wraps `speechSynthesis` (`canSpeak`, `speak` in `en-US` at rate 0.8, `stopSpeaking`) and only speaks straight from a tap, as iOS requires. `checkChoice` in `src/engine/choice.ts` checks a picked choice by index, for Spelling and Reading. `src/ui/format.ts` does all number and operator formatting. Colors, the radius scale, the spacing scale (docs/DESIGN.md §3, plus 40 and 48 for the practice layout) and the type scale (docs/DESIGN.md §4 and docs/DESIGN-PRACTICE.md §4) are CSS custom properties at the top of `src/index.css`: `--radius-*`, `--space-*` and `--text-N` (the font size in px, e.g. `--text-14`), with the older `--space`, `--gap`, `--gap-small` and `--radius` as aliases. `src/cssTokens.test.ts` checks their values and fails on a literal `border-radius`, `padding`, `margin` or `gap` from the scale and on a literal `font-size` (px, rem or em) anywhere in the stylesheet except the 24px on `:root` (#47). Component dimensions are still literal. `check-conventions` fails on a raw `<button>` or inline number formatting outside `src/ui/`, on words written straight into JSX instead of `src/copy.ts`, and on a hex color outside the tokens.
- **Answer boxes:** `StackedProblem` lays the problem out one digit per column with one answer box per column. `src/assignment/answer.ts` keeps her digits in the order she tapped them, and derives the boxes from them: ones place first for addition and subtraction, left to right (lined up under the ones column) for multiplication.
- **Layout:** the assignment renders through `src/screens/practice/PracticeFrame` (top bar, heading with the crumb and progress bar, activity row, actions row), styled by the px-only `.practice` block in `src/index.css` between its `practice: start` and `end` markers. It puts the number pad beside the problem from 1024px wide (landscape iPads, and a portrait 12.9-inch iPad Pro) and below it when narrower. The Math screen is two panels (`.practice-panel*`): the problem panel holds the eyebrow, the instruction and the stacked problem (`.practice .stacked` sets its 52px size, weight and `--digit` cell width; the base `.stacked` keeps only the grid and the tabular numbers), and the warm pad panel holds the heading and the pad, which the response replaces in the same panel at the same size. Nothing uses an `<input>`, so the iPad keyboard never opens. The pad ignores taps for 350 ms after it appears, so a double tap on Next can't type into the next problem; the action button does the same for 350 ms after it turns from Check to Next (`src/ui/useReadyAfter.ts`), so a double tap on Check can't skip her result. Padding respects the iPad's safe areas.
- **VoiceOver:** an always-present hidden live region reads each response, and focus moves to the action button (Next) after Check and to the pad after Next. On Spelling the live region also reads the finished message, focus goes to Play word after Next (or to the first choice when the iPad can't speak) and to Back to Home after Finish, which ignores taps for 350 ms like Next. On Reading, focus goes to Next on the passage, to the first question's first choice after Next, and to Done after Check answers; the live region reads each question's label and response after Check answers. Check answers and Done ignore taps for 350 ms like Next, so a double tap on Next can't also check. The choices are a radio group (one per question) with a roving tab stop: Arrow keys move to and pick the previous or next choice within that question.

## Saving results

SPEC §6.8. `src/storage/device.ts` keeps four `localStorage` entries: the device key, the unused seeds, the queue of results not yet sent (`{ seed, day, answers }`, the day being the iPad's own) and the Worker's latest state. Anything it can't parse reads as empty. Forgetting the key clears all four. With a key, the app asks for persistent storage (`navigator.storage.persist()`).

`src/sync/sync.ts`:

- **The seed in progress** is kept in memory with the key it came with, never stored: a closed app has nothing to resume, and the next top-up brings the seed back. `endSeed` queues her answers, or puts an unanswered seed at the back of the list; it does nothing if the key changed meanwhile.
- **`sync()`** runs one at a time; a call during a run joins it and makes it run once more. It sends queued results oldest first and removes each by seed once the Worker returns the recorded result (keeping its state), or refuses it as `bad_result` or `unknown_seed` (it can never be recorded). Any other answer holds that result and the rest for the next sync, but seeds still top up; no connection stops the sync. Each request gives up after 10 seconds. Then `POST /api/seeds`: the new list keeps stored seeds the Worker still lists, in their order, adds new ones, and leaves out queued and in-progress seeds, read again after the reply arrives. Last, `GET /api/state`. A 401 at any step forgets the key.
- **Projection** (`src/sync/projection.ts`, pure): `project` applies each queued result to the Worker's state, oldest first, with the engine functions and the Worker's rule that a day before the last counted day counts as that day. A bad item is skipped, as the Worker drops it. It doesn't model the Worker's day clamp; the Worker's numbers replace the projection after each sync. Home shows no numbers until the first state is stored.
- **When:** on load, whenever Home shows, after each result, and on the browser's `online` event.

## Data flow

- The browser loads the built app (`dist/`) as static assets from Cloudflare Workers. Any unknown path serves `index.html`.
- `/api` and `/api/*` reach the Worker first (`run_worker_first` in `wrangler.jsonc`). `GET /api/health` answers `{ "ok": true }` without a key. Every other route needs a device key (`Authorization: Bearer <key>`) and returns 401 without a valid one; an unknown route returns 404.
- **Parent routes** (`/api/parent/*`, `worker/parent.ts`): the Worker checks the Cloudflare Access token itself before anything else, so an unknown parent path is 401 too. `GET /api/parent/children` lists the children (id, name, grade, initials). `POST /api/parent/children` adds one (201) and `PATCH /api/parent/children/:id` renames one (`worker/children.ts`; neither takes `child`, there is no delete). Both check their fields with `src/parent/childFields.ts` (the pure rules the Add/Rename form uses too), write in one batch with an `admin_log` row (`child_add`, `child_rename` with before and after; a rename that changes nothing writes none), and the PATCH is revision-checked with 3 attempts, then 503 `busy`. Every other route is for one child, named by the `child` query parameter (`?child=2`): `childOf()` answers 400 `bad_child` for a missing or non-numeric id and 404 `unknown_child` for one that doesn't exist, before anything is read or changed; a device or result of another child is 404 like a missing one. Today: `GET /api/parent/summary`, `GET /api/parent/days` (the days of the seven ending on `today` with a finished result, oldest first, each once; the same `today` rule as the summary), `GET /api/parent/results` and `GET /api/parent/log` (read-only; the latest 50, newest first; the summary also returns `earnedToday`, the sum of `results.total` for her results of the `today` query parameter, 400 `bad_day` unless it is a real date within 1 day of the Worker's UTC date, and the UTC date when absent, and `completedToday`, the count of her finished results of the same day (left-early ones do not count), so `POST /api/parent/streak`, which answers with the summary, reports the UTC day's values, which nothing reads; each results row also carries `createdAt`), `GET /api/parent/devices`, `DELETE /api/parent/devices/:id` (unpair), `POST /api/parent/pairing-code` and `POST /api/parent/streak` (sets the streak and last counted day: validated first, then one D1 batch that updates her `children` row guarded by `revision` and inserts the log row only if that update applied; 3 tries, then 503); and `POST /api/parent/balance { amount, note }` (adds or removes Macaronis the same way, with its own guard: `balance` plus the new log row in one batch, 409 for a removal larger than the balance, 400 for a bad amount or note); `GET /api/parent/results/:id` (one result with its problems regenerated from its seed, beside her stored answers). No route changes a recorded result.
- **Pairing** (`worker/pair.ts`, SPEC §6.9): `POST /api/pair { code }` is the one write route with no key or token; the one-time code is the gate (CLAUDE.md). The code row carries the child it was made for (`pairing_codes.child_id`), and the new device gets that `child_id`; a new code voids any earlier unused one for any child. The preview code pairs a "Preview" device to the first child (lowest id), and answers 500 with no key when there is none. Each try is counted before its code is compared, in one `UPDATE … RETURNING` on the newest usable code, so a burst of tries at once gets at most 5 comparisons between them. The right code is claimed with a random value in the same batch that creates the device, so one code can't pair twice. Every refusal is the same `bad_code`. Before any of that, a Cloudflare rate-limit binding (`PAIR_LIMITER`, 10 tries a minute per `CF-Connecting-IP`, IPv6 counted by its /64 block) answers 429 to slow a flood of guesses (it can't stop slow ones from voiding a code; SPEC §6.9); without the binding, pairing is refused (503) rather than unguarded. Previews have their own limiter namespace.
- **The Access check** (`worker/access.ts`): `ctx.access` isn't passed to Workers that serve static assets, so the Worker verifies the `Cf-Access-Jwt-Assertion` token: RS256 only, signed by a key from `https://<team>/cdn-cgi/access/certs` (cached an hour; an unknown key id refetches at most once a minute), issuer `https://<team>`, audience `ACCESS_AUD`, not expired, with an email. It needs `ACCESS_TEAM_DOMAIN` and `ACCESS_AUD` and refuses everything without them. They're in `wrangler.jsonc`'s top-level `vars` (not secrets, and not the dashboard: each `wrangler deploy` replaces dashboard vars). Vars don't carry into the `previews` block, so previews never serve parent routes; keep it that way, since a parent token is checked by audience, not hostname.
- **The child API** (`worker/child.ts`, SPEC §6.8, §8): `GET /api/state`, `POST /api/seeds` and `POST /api/results`. The Worker regenerates each assignment from its seed and re-scores it with the engine, imported straight from `src/engine/`, so the app and the Worker can't disagree on the rules. The app calls it from `src/sync/sync.ts`. `GET /api/state` (and the `state` in a result) also carries the child's `name`, `grade` (her school grade, not an assignment grade) and `initials`; the iPad keeps them in `macworx.state` and `practiceChild()` (`src/sync/projection.ts`) hands them to the practice top bar. A request acts for its device's child: `deviceFor()` returns the device and its `child_id`, and every number and result is read and written on that child's row.

## Data

D1, one database per environment (see "Hosting"). STRICT tables, from `migrations/0001_init.sql`, `0002_admin_log.sql`, `0003_pairing.sql`, `0004_children.sql`, `0005_children_state.sql`, `0006_reading_passages.sql` and `0007_reading_results.sql`:

| Table | Holds |
|---|---|
| `devices` | Paired iPads: the SHA-256 of each device key (never the key), a label, and when it was revoked. |
| `seeds` | Seeds handed out, the device and day they went to, and whether a result used them. |
| `results` | Each recorded assignment of any kind as the Worker re-scored it: her answers (JSON), counts, grade and payout. `kind` is `math` (tied to a `seed`) or `reading` (tied to an `attempt`, with `seed` NULL and `detail` holding the passage title and each question's text, choices, her choice and the right choice as recorded, SPEC §6.8). A table CHECK keeps a row's kind, seed, attempt and detail consistent. A reading result's `answers` is her picks as JSON, `answered` the number of questions and `correct` the ones she got right. A recorded result never changes. Older `admin_log` rows with action `correction` may exist and still read in the activity log. |
| `pairing_codes` | Pairing codes: the code's SHA-256, the iPad's name, expiry, wrong tries, and when it was used or voided. Only the newest usable code counts. |
| `admin_log` | Every change a parent makes in admin mode (SPEC §5.3): when, which parent (Access email), the action and a JSON detail. Written in the same batch as the change. |
| `children` | One row per child: name, grade, initials, created_at and her own balance, streak, last counted day, completed and `revision`. The live copy of her numbers: the Worker reads and writes only this (see "Multiple children"). A parent restores a broken streak from the dashboard (`POST /api/parent/streak`), which edits `streak` and `last_day` here and changes `revision` in the same statement (see below). |
| `passages` | Reading passages (SPEC §6.10): title, genre, minutes, hint, text (paragraphs split by a blank line) and `image`, the picture's name in R2 (the passage id and an extension) or NULL. Ids are explicit in the owner's hand-run SQL files, so they match on preview and production; her next passage is the lowest id she hasn't finished. No passage text is in the repo. |
| `questions` | A passage's questions in `position` order. |
| `choices` | A question's choices in `position` order (1 to 4) and a `correct` flag. A unique index allows at most one correct choice per question. "Exactly four, exactly one correct" isn't a CHECK (a trigger's writes would count in D1's `meta.changes`), so the seed script (issue #213) will check it, and what the Worker does with one that fails is open (issue #214). Foreign keys stop deleting a passage that has questions. |
| `reading_attempts` | An attempt at a passage, handed out when she starts Reading: device, child, passage, the day it was handed out and whether a result used it. A reading result points at one attempt, once. An attempt handed out but never checked also stops a hand-run `DELETE FROM passages` for its passage (the foreign key), as a recorded result does. Her next passage (SPEC §6.10) joins her finished reading results to these rows by `attempt`; `reading_attempts_child_passage` serves that lookup. |
| `child` | Legacy: the one row the Worker used before `children`. Nothing reads or writes it since `0005`; it is stale from that migration on. |

- **One write at a time:** recording a result is one D1 batch. Its first statement updates the device's child's `children` row only if `revision` still has the value read before the write, and sets a new random revision. The result insert and the seed update apply only if the new revision is in place. So a lost race changes nothing; the Worker re-reads and retries (3 tries, then 503), and a repeat of the same seed returns the recorded result.
- **Multiple children (the API reads `children`):** SPEC §2 and §5.3 describe a household with many children, each device belonging to one child, and pairing codes made for a chosen child. `0004_children.sql` adds the `children` table (seeded with child 1, named "Child", copied from `child`) and `child_id INTEGER NOT NULL DEFAULT 1` on `devices`, `results`, `admin_log` and `pairing_codes` (no REFERENCES: SQLite ADD COLUMN; `0007` rebuilt `results` and kept that column as it was). It only adds; `child` keeps its `CHECK (id = 1)` and is not edited, so the running Worker is unaffected. Each child's balance, streak, last counted day, completed and `revision` live on her `children` row, so the guarded-by-`revision` updates switch from `child WHERE id = 1` to `children WHERE id = ?`. There is no trigger copying `child` to `children`: D1 counts a trigger's writes in `meta.changes`, and the Worker checks that it changed exactly 1 row. So until the API read `children`, `child` was the live copy. `0005_children_state.sql` copies `child` into `children` once more (balance, streak, last day, completed, revision of child 1), and from then on the Worker reads `children` and never `child`. Deploy gap: migrations run before the new Worker deploys, so a result or parent edit the old Worker makes between the copy and the deploy lands in `child` and is not copied (its `results` and `admin_log` rows are kept, with `child_id` 1). Rollback: rolling the Worker back to a version that reads `child` finds it stale, so first run `UPDATE child SET balance = (SELECT balance FROM children WHERE id = 1), streak = (SELECT streak FROM children WHERE id = 1), last_day = (SELECT last_day FROM children WHERE id = 1), completed = (SELECT completed FROM children WHERE id = 1), revision = (SELECT revision FROM children WHERE id = 1) WHERE id = 1`.
- **Editing by hand** (a fallback; the dashboard does this now): `UPDATE children SET streak = 5, last_day = '2026-10-17', revision = lower(hex(randomblob(16))) WHERE id = 1` (the child's id). Changing `revision` makes a result being recorded at that moment retry from the edited row rather than overwrite it.
- **Seeds and the app:** `POST /api/seeds` returns every seed the Worker still counts as unused, including ones the iPad has used offline but not synced yet. The app leaves out seeds in its result queue and the one in progress.
- **Migrations:** add the next numbered file in `migrations/`, never edit an applied one. Workers Builds applies them in the build step, before each deploy (see "Hosting"). `npx wrangler d1 migrations apply macworx --local` applies them to the local D1 for `npm run worker:dev`.
- **Pairing by hand:** `node scripts/create-device.mjs --local|--remote "label"` creates a device for the first child without a pairing code and prints its key once (it fails, printing no key, when there is no child). The Pair screen is the normal way (SPEC §5.4).
- **Tests** (`worker/*.test.ts`) run the Worker in Node against a real local D1 from Miniflare, with every migration applied. (`@cloudflare/vitest-pool-workers` doesn't support this repo's Vitest version.)

## Offline and install

`vite-plugin-pwa` generates the web app manifest and a service worker that precaches the built app, so the app opens with no connection (checked by `e2e/smoke.spec.ts`). `/api`, `/parent` and `/cdn-cgi` paths (with any query) are never served from the app shell: they always go to the network, so Cloudflare Access can ask a parent to sign in and finish signing in on this host (`src/networkOnly.ts`, tested). Icons are generated from `public/logo.svg` with `npx pwa-assets-generator` (`pwa-assets.config.ts`).

`public/_headers` sets the security headers for static assets. `vite preview` applies the same headers, minus HSTS, so a local production build runs under the production policy.

## Hosting

- `wrangler.jsonc` configures the Worker, its static assets and the D1 bindings.
- **Workers Builds** (Cloudflare's GitHub integration) builds every push. Its settings live in the Cloudflare dashboard:
  - Build command: `npm run build:cloudflare`. `scripts/cloudflare-build.mjs` applies D1 migrations to `macworx` when the branch is `main` and to `macworx-preview` for any other branch (from `WORKERS_CI_BRANCH`), then runs `npm run build`. The migration step lives in the repo, not in the dashboard's deploy fields, so it's reviewed and versioned; it refuses to run outside Workers Builds.
  - Deploy command (`main`): `npx wrangler deploy`. Preview command (other branches): `npx wrangler preview`.
  - Migrations run before the new code deploys, so each migration must also work with the code already running (add, don't rename or drop). The one exception is `0007_reading_results.sql`, which rebuilds `results` (the owner accepted a short failure window and minor data risk, issue #208). It copies every row with its id and keeps the old Worker working: the old Worker's INSERT names its columns, so `kind` takes its default `math`, and its reads name columns or take the whole row. It assumes D1 applies a migration file atomically, so no write lands between the copy and the swap; D1 rejects `BEGIN`/`COMMIT`, so the file defers foreign-key checks with `PRAGMA defer_foreign_keys`. If it fails, a result saved meanwhile stays on the iPad and is sent again.
- **Two D1 databases, both bound as `DB`:** `macworx` holds production data. `macworx-preview` is used only by preview URLs (the `previews` block), so a PR branch never touches her real data. A branch's migrations run on the shared preview database before it merges.
- `wrangler.preview-migrations.jsonc` exists only so wrangler can find the preview database for migrations; it can't see one that's only in the `previews` block. `worker/config.test.ts` checks the two configs name the same preview database, and that production and previews differ.
- Database IDs identify a database but grant no access, so they're committed. Cloudflare sign-ins and API tokens are never committed, and the build doesn't need any.
- **Preview pairing** (SPEC §6.9): `previews.vars.PREVIEW` is the mark; the code is the Worker secret `PREVIEW_PAIR_CODE` on the Preview base config, set with `npx wrangler preview base-config secret put PREVIEW_PAIR_CODE` (6 digits, not in the repo). `worker/pair.ts` accepts it only when `PREVIEW` is set, `ACCESS_AUD` is not, and the secret is 6 digits; it is checked after the rate limit. The client's `__PREVIEW__` build flag (`vite.config.ts`, from `WORKERS_CI_BRANCH` through `isPreviewBranch` in `src/previewBuild.ts`; `canPair` in `src/storage/device.ts`) shows the Pair button outside the installed app.
- `npm run worker:dev` builds the app and runs the Worker locally against a local D1.

### Writing and trimming tests

Tests are a running cost, and the Playwright job is the biggest part of it: the whole-assignment flows, which tap through every problem, take most of its time. Keep the suite small by reading before writing.

- **Read the existing tests first.** Before adding a test, read the ones for that screen or behavior (`grep` the spec for it). Extend or reuse one if it can cover the new case.
- **Delete or merge what is redundant.** If an existing test is redundant, overlaps a stronger one, or covers behavior that is gone, delete or merge it in the same PR. Say in the PR description what still covers each behavior you removed.
- **Run a test once when it can be.** A test that sets its own viewport, or does not depend on the engine or orientation, should run once per engine, not on every Playwright project. Tag it as the `test:e2e` row above and `playwright.config.ts` describe.
- **Skip waits that aren't under test.** A flow that taps through a whole assignment jumps past the pad's and Next's 350 ms ready delay with `fastClock` (before `page.goto`) and `skipReadyDelay` (`e2e/readyDelay.ts`). The delay itself stays covered on the real clock, for example by `a quick double tap on Check leaves her response on screen` and `a tap on the pad right after Next does not type into the next problem` in `assignment.spec.ts`.
- **Never trade coverage for speed.** Don't delete, skip or loosen a test or an assertion just to make CI pass or run faster. A removed run needs a named test that still covers it.
- **Find the slow ones.** The Playwright job's log lists every test with its time (`npx playwright test --reporter=list` prints the same locally). Look at the slowest few before anything else. The job took 6 to 8 minutes in November 2026; check the latest run rather than trusting that figure.
